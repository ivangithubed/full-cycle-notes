## 1. Етап і роль у життєвому циклі

**Бекенд-розробник** реалізує бізнес-логіку й дані: приймає запити від клієнта, перевіряє,
хто їх робить і чи має на це право, працює з базою даних і повертає відповідь. Саме тут
user story з першого стріму перетворюється на ендпоінти, правила й записи в базі.

## 2. Ключові ідеї

**.NET і C#.** C# — мова, .NET — безкоштовна кросплатформна платформа, яка компілює й
виконує код (підтримує також F# і Visual Basic). Шлях коду: `.cs` → компілятор → проміжна мова
(IL) у `.dll`/`.exe` → під час запуску JIT-компілятор перетворює її на машинний код.
За синтаксисом C# близький до C++ і Java; Python для новачка простіший.

**REST API.** REST — архітектурний стиль: ресурси мають URI, клієнт працює з ними через
стандартні HTTP-методи, а кожен запит самодостатній (сервер не тримає контекст сесії).

| Метод | Сенс | Приклад |
|---|---|---|
| GET | прочитати | `GET /restaurants/42` |
| POST | створити / виконати дію | `POST /restaurants` |
| PUT | повністю замінити | `PUT /restaurants/42` |
| PATCH | змінити окремі поля | `PATCH /restaurants/42` |
| DELETE | видалити | `DELETE /restaurants/42` |

Зміна пароля — скоріше PATCH (змінюєш одне поле).

**Коди відповіді:** `200` OK, `201` Created (може повертати створений об'єкт з ID — це
домовленість фронтенду й бекенду), `204` No Content (типово для оновлення чи видалення);
`400` некоректний запит, `401` немає дійсних облікових даних, `403` недостатньо прав,
`404` ресурс не знайдено, `409` конфлікт зі станом (наприклад, паралельні зміни),
`500` внутрішня помилка сервера (зазвичай нічого не пояснює — тоді йдуть до бекенд-команди),
`503` сервіс тимчасово недоступний.

**Архітектурні підходи:**
- **Шарова (layered):** презентація (приймає запит, обирає код відповіді) → бізнес-логіка
  (правила, валідація) → доступ до даних → БД. **Шар спілкується лише з сусіднім.** Обійти
  бізнес-шар — значить пропустити валідацію і зберегти невалідні дані.
- **Onion:** у центрі — доменна модель, яка нічого не знає про БД і UI; усі залежності
  спрямовані всередину (принцип Dependency Inversion з SOLID). Складніша, але гнучкіша.
- **Сервер/VM чи serverless:** у першому випадку ти керуєш процесом і середовищем,
  у другому — провайдер керує запуском і масштабом.

**Автентифікація ≠ авторизація.**
- Автентифікація — *хто звернувся?* (сесія, токен, термін дії).
- Авторизація — *що йому дозволено?* (роль, scope, власник ресурсу).
- Приклад: `DELETE /products/42` — звичайний користувач отримає `403`, адмін — `204`.
- **Ніколи не визначай права за ID з URL чи тіла запиту** — його легко підмінити. Користувача
  й ролі беруть з перевіреного токена.

**SQL vs NoSQL.**
- **SQL (реляційні: PostgreSQL, MySQL, MS SQL Server)** — таблиці з фіксованою структурою,
  зв'язки через первинні й зовнішні ключі, JOIN'и, транзакції; мова запитів спільна з
  невеликими відмінностями.
- **NoSQL (MongoDB, DynamoDB, Redis)** — документи чи пари ключ–значення, гнучка структура,
  легше масштабуються; мова запитів своя в кожної бази.
- Вибір під задачу: замовлення й платежі — реляційна (точність, транзакції); каталог з
  різними атрибутами — документна; кеш і сесії з TTL (time to live — строк, після якого запис зникає сам) — ключ–значення.
- **В одному проєкті можна поєднувати** (наприклад, PostgreSQL + Redis для кешу).
- SQL — мова запитів, а не формат даних, як JSON чи CSV.

> **Матеріали:** схеми архітектурних підходів, приклади запитів і відповідей, порівняння баз
> даних — дивіться презентації, які Ви отримали від організаторів.

## 3. Як це виглядало на навчальному проєкті

Шлях запиту: клієнт → **API Gateway** (єдина точка входу) → **Lambda на C#** (бізнес-логіка)
→ **DynamoDB** → відповідь тим самим шляхом. Бекенд побудовано за шаровою архітектурою.

Чесний компроміс, про який розповів лектор: дані проєкту за природою **реляційні**, але обрали
NoSQL DynamoDB — щоб залишитися в безкоштовному рівні хмари й у повністю serverless-архітектурі.
Це гарний приклад того, як контекст (бюджет, інфраструктура) переважує «ідеальну» відповідь
з підручника — дивись [стрім про архітектуру](/posts/13-architecture).

## 4. Скільки цього потрібно розробнику

- **Вміти:** читати й складати HTTP-запити, правильно інтерпретувати коди відповіді й показувати
  користувачу зрозумілі повідомлення; працювати з JSON; передавати токен у запитах.
- **Розуміти:** REST і семантику методів; різницю автентифікації та авторизації і чому права
  перевіряє сервер, а не клієнт; навіщо шари в бекенді; різницю SQL і NoSQL.
- **Знати:** як влаштована платформа .NET, onion/clean-архітектури, SOLID, транзакції й індекси.

## 5. ШІ в цьому блоці

**Що показали (теорія):**
- **Інструменти:** GitHub Copilot (розширення IDE — середовища розробки на кшталт VS Code — з автодоповненням), Claude Code (агент, що
  працює з усією кодовою базою), Cursor (IDE з вбудованим ШІ); також згадано Codex та
  Antigravity.
- **Три поняття:**
  - **агент** — ШІ-система з інструментами, що планує кроки, читає й змінює файли, запускає
    тести; описується `.md`-файлом з інструкціями під задачу; агенти можна об'єднувати в
    мультиагентну систему з оркестратором;
  - **скіл** — папка з інструкціями й скриптами для повторного використання, спільна для
    кількох агентів; формат сумісний між різними асистентами;
  - **промпт** — твій запит: задача, контекст, обмеження, очікуваний результат.
- **MCP (Model Context Protocol)** — «API для ШІ-агентів»: агент сам іде в трекер задач, бере вимоги з тікета й
  реалізує їх.
- **Правила приймання ШІ-коду:** читати diff; запускати збірку й тести; перевіряти доступ,
  валідацію, обробку помилок; не передавати ШІ паролі, токени й персональні дані;
  **відповідальність за merge і deploy — на людині**.

**Рівень:** L1–L4, але лише в теорії (за [шкалою залучення ШІ](/posts/02-ai-depth): L1 —
асистент у редакторі, L2 — агент у репозиторії, L3 — власні агенти й скіли, L4 — оркестрація).
Розповіли про весь цей спектр, без практики.
Практика — у [наступному стрімі](/posts/17-backend-practice).
