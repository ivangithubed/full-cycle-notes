## 1. Етап і роль у життєвому циклі

Це продовження DevOps: як **повторювано й без ручних кліків** створити всю інфраструктуру
проєкту і розгорнути в ній застосунок. Саме цей етап перетворює репозиторій на працюючий
сайт за посиланням.

## 2. Ключові ідеї

**Infrastructure as Code (IaC)** — інфраструктуру описують кодом, а не «клікають» у консолі
(підхід «ClickOps»). Навіщо:
- ручні дії — людський фактор і помилки;
- через кілька місяців ніхто не пам'ятає, що і як було створено;
- легко забути ресурс, який тихо списує гроші;
- одна команда — і та сама інфраструктура з'являється в будь-якому акаунті;
- можна описати сотні взаємопов'язаних сервісів.

**Terraform:**
- працює з багатьма провайдерами (AWS, Azure, GCP, навіть Kubernetes);
- зберігає **стан** (`tfstate`) — знає, що вже створено, і показує план змін;
- код ділять на файли й модулі (провайдер, змінні, окремі файли під кожен сервіс);
- основний цикл: `terraform init` → `plan` → `apply`, прибирання — `destroy`;
  перевірки — `fmt` і `validate`.

**AWS Syndicate** — інструмент для serverless, де розробники описують ресурси (Lambda,
API Gateway, DynamoDB) поруч зі своїм кодом.

**Навіщо два інструменти:** Terraform — для базової інфраструктури, яка змінюється рідко
і може містити сервіси, що Syndicate не підтримує. Syndicate — для частини, яку розробники
змінюють разом з кодом хоч кілька разів на день (нові маршрути, індекси таблиць), не чекаючи
DevOps.

**Безпечний доступ до хмари:**
- **не працювати з root-акаунтом**, до якого прив'язана платіжна картка;
- створити окремого IAM-користувача (IAM, Identity and Access Management — сервіс AWS для
  користувачів, ролей і прав) і ключ доступу для CLI (command line interface — роботи з хмарою
  командами в терміналі) (у демо — з правами адміністратора
  «для простоти»; у реальному житті — мінімально необхідні права);
- ключі — лише в локальних конфігах, ніколи в репозиторії.

**Стан Terraform у спільному сховищі** (S3-бакет з версіонуванням і закритим публічним
доступом) — щоб усі, хто працює з інфраструктурою, і CI бачили той самий стан.

**Назви бакетів містять ID акаунта** — бо імена S3-бакетів глобально унікальні.

## 3. Як це виглядало на навчальному проєкті

**Порядок розгортання:**
1. **Terraform** — спільна інфраструктура (Cognito, SQS, S3 для фронтенду, CloudFront тощо).
   Одразу після цього сайт за посиланням CloudFront відповідає «Access Denied» — це нормально,
   фронтенду ще немає.
2. **Syndicate** — бекенд: Lambda-функції, API Gateway з маршрутами, таблиці DynamoDB
   (`build` → `deploy`; займає кілька хвилин).
3. **Фронтенд** — дізнатися адресу API, зібрати застосунок з цією адресою і синхронізувати
   зібрані файли в S3.

> **Матеріали:** точні команди, змінні й порядок кроків — дивіться презентації та інструкцію
> до проєкту, які Ви отримали від організаторів.

Якщо за адресою CloudFront відкривається сторінка з входом і бронюванням — усе зроблено
правильно.

**Оновлення під час роботи:** змінився лише код бекенду — `update`; з'явилися нові ресурси чи
маршрути — повний `deploy`; фронтенд — знову зібрати й синхронізувати.

**Видалення — у зворотному порядку** і командами, а не руками (руками щось обов'язково
пропустиш): очистити бакет фронтенду → прибрати бекенд → `terraform destroy` → видалити
службові бакети (версіонований бакет зі станом спершу треба повністю очистити в консолі).
Поки проєкт потрібен — інфраструктура коштує центи; але звичка прибирати за собою рятує
від неприємних рахунків на платних акаунтах.

**Демо з нуля:** мінімальна Lambda в Terraform — провайдер, архівування коду, функція і
IAM-роль, яку функція «приймає» на себе; далі до неї вручну додали HTTP API з двома
маршрутами. Самостійна вправа після стріму — описати в Terraform і функцію, і API Gateway.

## 4. Скільки цього потрібно розробнику

- **Вміти:** розгорнути проєкт за інструкцією з README; задавати змінні середовища для збірки
  (адреса API); працювати з AWS CLI на рівні «подивитися, що створено»; прибрати за собою.
- **Розуміти:** що таке IaC і стан; чому не працюють з root-акаунтом; навіщо `plan` перед
  `apply`; різницю між оновленням коду і зміною інфраструктури.
- **Знати:** як влаштовані провайдери й модулі Terraform, що є альтернативи (CloudFormation,
  Pulumi) і коли потрібен Docker.

## 5. ШІ в цьому блоці

**Що показали:** практично нічого — усе робилося вручну за заздалегідь підготовленим
прикладом. Лектор розповів, що в роботі спершу сам досліджує питання, а ШІ використовує,
щоб перевірити або підтвердити свою гіпотезу; для автоматизації в команді — ШІ-рев'юер
pull request'ів.

**Рівень:** L0 — чат (за [шкалою залучення ШІ](/posts/02-ai-depth) від L0 «чат» до L5 «ШІ в
процесі команди»), і то лише в розповіді: у самому розгортанні ШІ участі не брав.

**Як могло бути глибше:** агент, який читає README і виконує розгортання крок за кроком,
зупиняючись перед кожною командою, що змінює хмару; агент, що аналізує вивід `terraform plan`
і пояснює, що буде створено чи знищено; підключення агента до хмари через MCP-сервер (MCP, Model Context Protocol — стандартний спосіб
дати ШІ-агенту доступ до зовнішньої системи) з
обмеженими (лише читання) правами.
