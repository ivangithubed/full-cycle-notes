## 1. Етап і роль у життєвому циклі

**Фронтенд-розробник** — міст між продуктом, користувачем і даними. Він перетворює макети
дизайнерів і вимоги аналітиків на інтерфейс, з'єднує його з бекендом через API і першим
бачить, що «щось не так», бо його код безпосередньо торкається користувача. Тому фронтенд
постійно комунікує з усіма: дизайном, BA (бізнес-аналітиком), бекендом.

Обов'язки сьогодні — далеко не лише «додати форму й кнопку»: робота з бекендом, швидкодія
(користувач не чекатиме більше кількох секунд — піде до конкурента), доступність, тести,
підтримка й дебаг коду.

## 2. Ключові ідеї

**Фундамент — HTML, CSS, JavaScript.** Фреймворки з'являтимуться й зникатимуть, але всі вони
стоять на цих трьох технологіях. Лектор чесно визнав власну помилку на старті: одразу взявся за
фреймворк, не зрозумівши базу, — і радить так не робити. Знаючи базу, перейти з одного
фреймворку на інший — це переважно новий синтаксис.

**HTML — структура і сенс сторінки.** Він будує DOM-дерево, з яким далі працюють CSS і
JavaScript, але сам не дає ні стилів, ні поведінки.

**Семантика й доступність:**
- семантичні теги (`header`, `section`, `article`, `button`) і правильна ієрархія заголовків
  (`h1` → `h2` → `h3`) пояснюють скрінрідерам і пошуковим ботам, де що на сторінці;
- `alt` у зображення — це текст, який побачить людина, якщо картинка не завантажилась, і який
  прочитає скрінрідер;
- «кнопка» з `div` виглядає так само, але скрінрідер її не помітить як кнопку — людина з
  порушеннями зору просто не знайде «Оформити передзамовлення»;
- популярне питання на співбесіді: як зробити з `div` доступну кнопку? Потрібні `role="button"`,
  `tabindex`, обробник кліку **і** підтримка клавіатури. Простіше — взяти справжній `button`;
- перевіряти семантику, доступність і швидкодію сторінки зручно через Lighthouse.

**CSS — каскад.** У кожного селектора є «вага» (специфічність), є шари й порядок оголошення —
так визначається, яке правило переможе. **Препроцесори** (SCSS, Sass, Less) дають змінні,
спільні стилі й зручніший синтаксис, але все одно компілюються у звичайний CSS. На проєкті —
SCSS; лектор погодився з чатом, що з розвитком сучасного CSS препроцесори поступово втрачають
потребу.

**JavaScript — двигун застосунку:** змінює сторінку без перезавантаження. Ключові речі, про які
питають на співбесідах:
- JS **однопотоковий**, а асинхронність забезпечує **event loop** з чергами задач різного
  пріоритету (мікрозадачі, як-от проміси, і макрозадачі, як-от таймери);
- **динамічна типізація** — тип змінної визначається під час виконання, і неявні перетворення
  можуть дати несподіваний результат;
- поріг входу низький: достатньо браузера; а знання JS відкриває сервер (Node.js), мобільні
  (React Native) і десктопні (Electron) застосунки — але й конкуренція там велика.

**TypeScript — статична типізація.** Тип відповіді API описують інтерфейсом — і одразу видно,
які поля прийдуть і якого вони типу. Але **типи не гарантують, що бекенд справді поверне саме
це**: для перевірки даних під час виконання використовують схеми валідації (наприклад, Zod).
І навіть тоді нове чи змінене поле з бекенду може зламати прод, якщо цей випадок не обробили.

**SPA (single page application):** сторінка завантажується один раз, а далі JavaScript
підміняє лише потрібні частини. На проєкті `index.html` і JS-бандл лежать у S3 і роздаються
через CloudFront, а переходи між сторінками обробляє роутер Angular без звернення до сервера.

**Навіщо фреймворки:** компоненти, які перевикористовуються; роутинг без перезавантаження;
реактивність (інтерфейс оновлюється сам, коли змінились дані); робота з API; інструменти —
збірка, тести, лінтери; єдині домовленості для всієї команди.

**React чи Angular — це як молоток чи плоскогубці:** кожен для свого.

| Критерій | React | Angular |
|---|---|---|
| Що це | бібліотека для інтерфейсу (Meta) | повноцінний фреймворк (Google) |
| Мова | JavaScript або TypeScript | TypeScript за замовчуванням |
| Реактивність | virtual DOM і хуки | сигнали і change detection |
| Роутинг, HTTP, форми | сторонні бібліотеки | вбудовано |
| Структура проєкту | на розсуд команди | задана фреймворком і CLI |
| Мобільні застосунки | React Native | NativeScript |

- **Virtual DOM** — копія DOM у вигляді об'єктів: змінюються дані → порівнюється з попередньою
  копією → у справжньому DOM оновлюється лише змінене (бо зміни DOM — одна з найдорожчих
  операцій).
- **Хуки** (`useState`, `useEffect`) — спосіб працювати зі станом і побічними ефектами в
  компонентах-функціях. `useEffect` без прибирання за собою може «покласти» браузер.

**Angular детальніше:**
- **плюси:** усе з коробки; TypeScript; одна структура для всієї команди (швидший онбординг);
  впровадження залежностей; сигнали; інструменти генерації, збирання й тестів; регулярні
  мажорні релізи приблизно раз на пів року від Google;
- **мінуси:** вищий поріг входу (усе й одразу); часті мажорні релізи вимагають міграцій —
  оновлювати краще по одній версії (19 → 20 → 21 → 22), а не стрибком; важчий бандл (на проєкті
  близько 920 КБ при ліміті 1 МБ у конфігу), який зменшують «лінивим» завантаженням сторінок
  лише тоді, коли вони потрібні;
- **як Angular дізнається, що треба оновити екран:** класично Zone.js перехоплює всі асинхронні
  події й після кожної перевіряє дерево компонентів зверху донизу — працює, але з зайвою
  роботою. **Сигнали** дають точкову реактивність: змінився `signal` → перерахувався залежний
  `computed` → `effect` виконав побічну дію → оновилась лише та частина шаблону, яка їх читає;
- **standalone-компоненти** самі описують свої залежності, без старих модулів; `inject()` замість
  впровадження через конструктор; нові `input()`/`output()`.

**Великий проєкт — велика відповідальність.** Великим вважають проєкт з багатьма функціями,
сторінками й даними (маркетплейс із фільтрами, пошуком, сортуванням, ШІ-помічниками). У
проєктах без жорсткої структури під тиском дедлайнів накопичуються «костилі» — тимчасові
обхідні рішення, які стають технічним боргом.

## 3. Як це виглядало на навчальному проєкті

- **Стек:** Angular 22, нещодавно мігрований з 19 — частину коду переписали, частина ще чекає
  (лектор прямо назвав це технічним боргом). Стилі — SCSS.
- **Ролі:** клієнт (меню, бронювання, передзамовлення, відгуки, запрошення гостей), офіціант
  (бачить бронювання, підтверджує чи відхиляє, отримує сповіщення), адміністратор (локації).
- **Структура:** сторінки — в `pages`; функціональні компоненти групуються за доменом (кошик,
  бронювання); спільні компоненти (кнопки, поля, форми) — в `shared`; сервіси — робота із
  запитами, по одному на напрям; моделі — інтерфейси даних. Щоб «спільна» папка не стала
  смітником, туди виносять лише справді повторні компоненти — і тут багато залежить від того,
  наскільки повторно використовуваним зробили дизайн.
- **Обробка відповідей API:** кожен код відповіді (2xx, 4xx, 5xx) має свою реакцію в інтерфейсі —
  зрозуміле повідомлення («тости» — невеликі сповіщення), сторінка помилки чи «технічні роботи»,
  а не порожній екран чи загальне «Error».
- **Домовленості коду:** сигнали → `computed` → `effect`, без нових `Subject` для стану; RxJS
  лишається для HTTP; строгий TypeScript без `any`; у SCSS — `@use` замість імпортів.
- **Процес:** кожна зміна — через pull request з лінтером, перевіркою типів і збиранням; ШІ-бот
  пише коротке резюме змін і поради.

**Практика після стріму — три рівні:**
1. **Верстка** екрана зведеного замовлення власника броні за макетом у Figma: що замовив кожен
   гість і загальна сума. Можна використати власний дизайн.
2. **Групове передзамовлення на моках** — без бекенду: застосунок запускається в демо-режимі з
   тестовими даними, а сервіси повертають заздалегідь підготовлені відповіді.
3. **Інтеграція з власним бекендом** — підключити ендпоінти, реалізовані в
   [бекенд-практиці](/posts/17-backend-practice), до фронтенду, розгорнутого у власному
   хмарному акаунті.

Для кожного рівня є готові автоматичні тести, які можна запустити однією командою й побачити,
що вже виконано, а що ні.

> **Матеріали:** архів фронтенду з інструкцією, описом рівнів, тестами й макетом — дивіться
> матеріали, які Ви отримали від організаторів.

## 4. Скільки цього потрібно розробнику

Для фронтенд-розробника цей блок — спеціалізація, тож тут глибина максимальна. Мінімальний
набір навичок джуніора за лектором:
- **Вміти:** HTML і семантика, CSS і препроцесори, JavaScript (найбільше питань на співбесідах),
  TypeScript (інтерфейси, типи, дженерики), один із фреймворків, робота з API, Git,
  юніт-тести (Jest тощо), дебаг; англійська на рівні B1–B2; уміння працювати з ШІ-асистентами
  й перевіряти їхній код.
- **Розуміти:** event loop, як фреймворк вирішує, що перемалювати (virtual DOM чи сигнали),
  SPA й бандл, коди відповіді API, доступність.
- **Знати:** різницю між фреймворками й бібліотеками, екосистеми (серверний рендеринг,
  мобільні застосунки), схеми валідації даних.

Для інших ролей — розуміти, що фронтенд обробляє кожну відповідь бекенду і що доступність —
не прикраса, а вимога.

Поради лектора новачкам: більше практики й власних проєктів; учитися на задачах, які хочеться
автоматизувати для себе; вік не перешкода — у ІТ приходять і після сорока. І ще одна:
**бути трохи «фулстек»** — розуміти і фронтенд, і бекенд.

## 5. ШІ в цьому блоці

**Що показали:**
- **ШІ-рев'юер pull request'ів** (як і в DevOps-стрімі): збирає резюме змін і поради. Лектор
  чесно додав, що він не завжди точний — не має повного контексту й зазвичай працює на
  дешевшій моделі;
- **`CLAUDE.md`** — загальні правила для агентів і опис структури репозиторію: агент спершу
  читає його, а не весь проєкт, і витрачає менше токенів;
- скіли й агенти під окремі задачі (пошук багів, документація);
- **головне правило: ШІ нічого не комітить без згоди людини.** Усе, що агент зробив від твого
  імені, — твоя відповідальність.

**Формула промпту:**
1. **Контекст** — стек, потрібні файли, що використовуємо, а що ні;
2. **Задача** — одна, з чітким результатом і без побічних ефектів;
3. **Обмеження** — що можна чіпати, а що ні;
4. **Формат** — у якому вигляді чекаємо результат; на старті — режим плану, щоб бачити, що ШІ
   збирається робити, перш ніж він це зробить;
5. **Перевірка** — як переконатися, що готово: тести, перевірка типів, очікуваний результат.

**Цикл роботи: Explore → Plan → Code → Verify.** Спершу ШІ лише читає код і нічого не змінює;
потім узгоджуєте, що змінювати; потім код — конкретними кроками; наприкінці — перевірка
(запустити TypeScript, тести тощо).

**П'ять правил контексту:**
1. одна задача — одна сесія; нова задача — новий чат (залежні задачі, як-от вхід і реєстрація,
   можна в одній сесії; незалежні — розділяти);
2. не виходить — очистити контекст і сформулювати чіткіший промпт, а не повторювати те саме;
3. вказувати конкретні файли;
4. давати приклад: «зроби так само, як тут»;
5. делегувати читання й дослідження субагенту, щоб не засмічувати основний контекст.

**Що працює:**
- **інтерв'ю** замість довгого промпту: описати мету й обговорити з ШІ підходи, а вже потім
  ставити задачу;
- **автор і рев'юер** — рев'ю у свіжій сесії без зайвого контексту;
- **кілька варіантів** з плюсами й мінусами, рішення — за людиною;
- **«поясни»** — чудовий спосіб вивчати нову технологію.

**Чого уникати:** «зроби все» без контролю; повторювати те саме в тій самій сесії, коли не
виходить; приймати код не читаючи; ділитися токенами, паролями й чутливими даними (особливо на
безкоштовних і особистих підписках).

**Окремо для новачків:** спершу щось написати руками — так краще запам'ятовується. Якщо руками
повністю не хочеться — попросити ШІ пояснити розв'язок покроково, розібратися з кожним кроком
і потім написати самому. Великий антипатерн — «напиши мені все».

**Рівень:** L5 у процесі команди (ШІ-рев'юер у CI, вузька роль) і L3 у розробці (`CLAUDE.md`,
скіли й агенти під проєкт) — за [шкалою залучення ШІ](/posts/02-ai-depth) від L0 «чат» до L5
«ШІ в процесі команди». Крім того — найповніша на інтенсиві **методологія** роботи з ШІ,
хоча й у формі порад, а не демонстрації.

**Як могло бути глибше:** показати цикл Explore → Plan → Code → Verify наживо на домашньому
завданні: агент читає готові тести рівня, пише план, людина схвалює, агент реалізує, а тести
стають критерієм готовності.

## 6. Самоперевірка

1. Чому `div` з обробником кліку — погана кнопка? Що треба додати, щоб вона стала доступною?
2. Чим TypeScript-інтерфейс відповіді API відрізняється від валідації даних схемою?
3. Що таке SPA і як роутер змінює сторінку без запиту до сервера?
4. Як Angular дізнається, що треба оновити екран: Zone.js проти сигналів?
5. Назви п'ять частин формули промпту і чотири кроки циклу роботи з ШІ.
